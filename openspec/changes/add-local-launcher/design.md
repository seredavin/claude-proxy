## Context

Мотивация — в proposal.md, требования — в `specs/local-launcher/spec.md`.

От чего отталкиваемся (состояние после `add-plain-listener`):

- `dispatch()` в `main.go` — плоский `switch` по имени команды; каждая
  команда строит свой `flag.FlagSet`, вызывает `config.Bind(fs)` и общий
  `resolve(raw, fs, envFile)` (флаги → файл → окружение).
- `server.Run(ctx, cfg, log)` — блокирующий: сам делает `net.Listen`,
  сам гасит сервер по отмене `ctx`. Наружу не сообщает ни о готовности,
  ни о фактическом адресе слушателя.
- `clientenv.Render(cfg, token)` — печатает блок `export …` строкой;
  какие именно переменные и значения — знает только он.
- `service.waitHealthy()` — опрос `/healthz` снаружи, для `install`.
- `auth.Generate()` (используется `gen-token`) — генерация пропуска.
- Прототип на bash из обсуждения: фоновый процесс + опрос `/healthz` +
  `trap` — работает, но это отдельный файл вне поставки, только bash/curl.

## Goals / Non-Goals

**Goals:**

- Одна команда вместо двух терминалов и шести `export`. Никаких новых
  файлов в поставке: только бинарь.
- Переиспользовать `config`, `server`, `clientenv`, `auth` как есть; новая
  логика — только оркестрация.
- Звено и `claude` — один жизненный цикл: не бывает «звено осталось висеть»
  и «`claude` запущен, а звено не поднялось».
- Интерфейс `claude` не засоряется логом шлюза.

**Non-Goals:**

- Демон/агент «локальное звено всегда запущено» (launchd, systemd --user).
  `install` на Linux уже покрывает постоянный вариант; здесь — сессия.
- Хранение токена подписки шлюзом. Он проходит транзитом из окружения в
  окружение, как и раньше.
- Поддержка Windows в части сигналов. Код собирается, `Ctrl+C` в консоли
  ведёт себя по правилам Windows; отдельно не тестируется.
- Проверка доступности внешнего шлюза до запуска `claude`. Ошибка
  соединения покажется в первом же запросе и в логе; предварительный
  «пинг» удлиняет старт и дублирует диагностику.

## Decisions

### D1. Go-подкоманда `local`, а не shell-скрипт в поставке

Согласовано с пользователем. Поставка проекта — один бинарь и образ;
скрипт пришлось бы качать отдельно, он не работает без bash и curl, а его
настройки жили бы в своём формате рядом с `CLAUDE_PROXY_*`. Подкоманда
получает конфигурацию через тот же `config.Bind`/`resolve`, готовность
узнаёт без гонки по порту и собирается под все платформы релиза.

Альтернатива — `scripts/claude-local.sh` как ассет релиза. Отвергнута:
вторая система конфигурации и зависимость от внешних утилит.

### D2. Звено в горутине того же процесса, готовность — через callback

`server` получает `RunReady(ctx, cfg, log, ready func(net.Addr)) error`;
существующий `Run` становится `RunReady(…, nil)` и не меняет поведения.
`ready` зовётся сразу после успешного `net.Listen` основного слушателя (до
`Serve` — сокет уже принимает соединения в очередь) с фактическим адресом.

Почему не опрос `/healthz` через `service.waitHealthy()`: он привязан к
`127.0.0.1` и известному порту, а нам нужен порт `0` (D4); и это гонка с
таймаутом там, где есть точный сигнал. Почему не отдельный процесс
`claude-proxy run` под `exec`: два процесса вместо одного, свои сигналы,
свой pid — ради ничего.

### D3. Оркестрация в `internal/launcher`, `main.go` — только флаги

Новый пакет `launcher` с одной точкой входа
`Run(ctx, Options) (exitCode int, err error)`: поднимает звено, ждёт
`ready`, собирает окружение, запускает дочерний процесс, разруливает
сигналы и завершение. `cmdLocal` в `main.go` — разбор флагов, `resolve`,
проверки-отказы и вызов `launcher.Run`. Так оркестрация тестируется без
`claude`: в тестах вместо него — любой исполняемый файл (`/bin/sh -c`).

### D4. `--listen` по умолчанию `127.0.0.1:0`

Свободный порт петли. Ни один стенд не сломается из-за «порт 9443 занят»
прошлым экземпляром или установленным шлюзом; фактический порт попадает в
`ANTHROPIC_BASE_URL` из адреса слушателя (D2). Явный `--listen` работает по
правилам `--tls none`: `validate()` проверяет loopback, `local` ничего не
добавляет.

Альтернатива — фиксированный `127.0.0.1:9443` как у `run`: удобнее для
`curl` руками, но ради этого есть `--listen`.

### D5. Клиентские переменные — из `clientenv`, парами

`clientenv` получает `Vars(cfg, token) []Var` (`Var{Name, Value, Unset bool}`),
а `Render` печатает их. `local` берёт `Vars` с копией `cfg`, где `Listen`
заменён на фактический адрес, и накладывает на `os.Environ()`: `Unset` —
удалить, остальное — задать. Так `local` и `client-env` не могут разойтись
в наборе переменных; для `ModeAPIKey` всё работает без отдельной ветки.

`ANTHROPIC_AUTH_TOKEN` в режиме `oauth` — не из `Vars` (там плейсхолдер),
а из окружения `local` с учётом `--env-file`: `resolve` уже читает файл в
`Getenv`, значение берётся через него же. Отсутствие — отказ до старта звена.

### D6. Пропуск звена: сгенерировать, если не задан

Если после `resolve` `Tokens` пуст — `auth.Generate()` под меткой `local`,
и только тогда `config.Resolve` пройдёт проверку «ни одного токена». Порядок:
`ApplyEnv` → если `raw.Tokens == ""` — подставить → `Resolve`. Заданные
явно (флаг, `CLAUDE_PROXY_TOKENS` в файле или окружении) — как есть, первый
из набора уходит `claude`, как в `client-env`.

Пропуск не пишется ни в файл, ни в лог: живёт в памяти процесса и в
окружении `claude`.

### D7. Обязателен `--upstream-key`

Локальное звено без внешнего шлюза — прямой путь на Anthropic через лишний
процесс; это не сценарий, а забытая настройка. Проверка в `cmdLocal` после
`resolve`: пустой `UpstreamKey` — отказ с текстом про цепочку и оба
параметра. Проверку «ключ при дефолтном апстриме» уже делает `validate()`,
поэтому непустой ключ гарантирует и не-дефолтный апстрим.

### D8. Сигналы и завершение

- Дочерний процесс наследует stdin/stdout/stderr и терминал; `Ctrl+C`
  доставляется всей группе. Запускатель на время жизни `claude` подписан
  на `SIGINT` через `signal.Notify` и просто не реагирует: `claude` сам
  решает, прерывать ли генерацию или выходить, а звено не должно исчезнуть
  под ним. Именно `Notify`, а не `signal.Ignore`: диспозиция `SIG_IGN`
  переживает `exec` и досталась бы `claude`, а обработчик Go в ребёнке
  сбрасывается в умолчание.
- `SIGTERM` (например, от закрытия терминала) — тот же `Notify`, пересылка
  дочернему процессу, дальше — обычное ожидание.
- После выхода `claude`: отмена `ctx` звена, ожидание `RunReady`, возврат
  кода выхода `claude` (`ExitError.ExitCode()`; убит сигналом — `1`).
- Звено вернуло ошибку раньше `claude`: `SIGTERM` дочернему, ожидание,
  возврат ошибки звена — код `1`, текст в stderr через обычный путь
  `main()`.

### D9. Лог в файл, одна строка в stderr

Логгер звена — `newLogger`-подобный, но в `*os.File` (`--log-file`,
`O_APPEND|O_CREATE`, каталог `MkdirAll`). Формат — тот же `--log-format`.
На stderr перед `exec` — одна строка:
`локальное звено http://127.0.0.1:54321 → https://edge…:9443, лог: <путь>`.
Дефолт пути: `$XDG_STATE_HOME/claude-proxy/local.log`, без переменной —
`~/.local/state/claude-proxy/local.log` — это место для логов по XDG, и
на macOS оно тоже приемлемо. Файл настроек — `~/.config/claude-proxy/local.env`
(`$XDG_CONFIG_HOME` при наличии): туда же ведёт документация, там же его
ждёт пользователь после прототипа.

### D10. Поиск `claude`

`--claude` (умолчание `claude`) → `exec.LookPath`. Не найден — отказ до
старта звена с текстом «не найден `claude` в PATH; путь можно задать
`--claude`». Не запускаем звено ради того, чтобы через секунду упасть.

## Risks / Trade-offs

- [Claude Code перехватывает `SIGINT` иначе, чем ожидается — например,
  выходит по первому `Ctrl+C` в `-p`-режиме] → Это его поведение, не наше:
  звено гасится по факту выхода, ничего не течёт. Проверить на стенде.
- [Диспозиция `SIGINT` родителя достаётся `claude`] → `Notify` вместо
  `Ignore` (D8). Покрыть тестом: дочерний `sh` получает `SIGINT` от
  запускателя и завершается, то есть сигнал у него не игнорируется.
- [Токен подписки в `local.env` рядом с пропуском внешнего шлюза] → Файл
  пользовательский, права `0600` рекомендуются в документации; шлюз его не
  создаёт и не проверяет права. Токен и так лежал в shell-профиле.
- [Порт `0` мешает отладке `curl`-ом] → `--listen 127.0.0.1:9443` явно;
  адрес печатается в stderr и в логе.
- [Лог растёт без ротации] → Объём мал (старт/стоп/ошибки, запросы по
  одной строке); ротацию не делаем, путь известен, файл можно удалить.
- [Отсутствие `~/.local/state` на macOS выглядит чужеродно] → Каталог
  создаётся сам; путь всегда печатается.

## Migration Plan

Новая команда, существующие не меняются; `server.Run` и `clientenv.Render`
сохраняют сигнатуры и поведение. Откат — прежний бинарь. Файл
`~/.config/claude-proxy/local.env` — обычный `EnvironmentFile`, его можно
подать и в `run --env-file`.

Прототип `~/bin/claude-local` из обсуждения после выхода команды становится
не нужен: `alias claude-local='claude-proxy local'`.
